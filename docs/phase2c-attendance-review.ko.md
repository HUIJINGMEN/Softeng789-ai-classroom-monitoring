# Phase 2C — 교사 출석 검토 화면

[English guide](phase2c-attendance-review.md)

브랜치: `DoJun/phase2c-attendance-review`. Phase 2B의 `ea02753` 커밋에서 시작했습니다.

## 달라진 점

교사·관리자의 수업 상세 화면에 **Attendance review**를 추가했습니다.

| 화면 | 의미 |
|---|---|
| Present / Late / Absent | 저장된 출석 / 지각 / 결석 |
| Awaiting approval | 아직 출석이 저장되지 않은 유효한 학생 요청 |
| Not recorded | 저장된 출석도 유효한 대기 요청도 없는 학생. 자동 결석 처리는 하지 않습니다. |
| Student check-in requests | 교사가 검토할 학생 요청과 선택 승인·반려 버튼 |
| Class attendance | 학생 이름·학번 검색, 상태 필터, 수동 수정 |
| Processing history | 최근 처리 이력 최대 100건 |
| All check-in requests | 승인·반려·만료를 포함한 요청 내역 |

학생 한 명을 한 행에 표시하는 통합 표를 사용합니다. 승인 대기 → 미처리 → 저장된 출석 순서이며 같은 그룹 안에서는 이름순입니다. 20명까지 한 페이지에 표시하고 21명부터 Previous/Next로 이동합니다. 상단 상태별 숫자를 누르면 필터링하며 이름·학번으로 검색할 수 있습니다. 휴대폰에서는 짧은 목록으로 표시합니다. 기존 상세 출결 표는 **Attendance details and check-in times**를 펼치면 확인할 수 있습니다.

화면을 보고 있을 때 15초마다 갱신하며 **Refresh**로 바로 갱신할 수도 있습니다. 사진 인식 모델·기준값, 가입 및 관리자 승인, 교사 사진 업로드, 수동 출석은 유지됩니다. 실시간 모니터링이나 자동 출석 기능을 추가한 것은 아닙니다.

## 테스트 순서

1. 교사와 학생을 서로 다른 브라우저 프로필 또는 일반 창·시크릿 창으로 로그인합니다. 같은 브라우저 프로필의 탭끼리는 로그인 쿠키를 공유합니다.
2. 학생이 등록된 수업 중 출석 요청이 가능한 시간의 수업을 선택합니다. 출석 시간이 아니면 요청할 수 없으며, 이미 출석이 저장된 학생도 새 요청을 할 수 없습니다.
3. 학생이 웹캠 사진으로 출석 요청을 제출합니다.
4. 교사는 **Attendance → 해당 수업 상세 → Attendance review**에서 요청이 최대 15초 내 표시되는지 확인합니다.
5. 실제 수업 참여를 확인한 학생의 체크박스를 선택합니다. 얼굴 일치만으로 실시간 참여가 증명되지는 않습니다.
6. **Approve selected**로 승인합니다. 지각이면 **Mark selected late**, 반려하려면 **Reject selected**를 사용합니다. 체크한 학생 행의 Approve/Reject로 한 명씩 처리할 수도 있습니다.
7. Present 수가 바뀌고 해당 학생이 승인 대기에서 빠지는지 확인합니다. 학생 화면도 새로고침해 저장된 상태를 확인합니다.
8. **Processing history**를 펼쳐 학생·처리자·처리 내용·전후 상태·시간을 확인합니다.
9. 학생 행의 **Manual** 또는 **Correct**를 눌러 기존 수동 수정 창에서 수정해 봅니다. 이 화면에는 다음 자동 갱신 또는 수동 새로고침 후 반영됩니다.
10. 두 학생으로 테스트할 수 있을 때 선택 승인과 부분 실패를 확인합니다. 새 요청이 들어와도 자동으로 선택되어서는 안 됩니다.

현재 한 사람의 얼굴로만 실제 인식을 확인했으므로 다른 사람·기기·환경에서의 인식 정확도 검증은 별도로 남아 있습니다. 이번 자동 UI 테스트의 여러 학생은 가상 데이터입니다.

## 여러 학생 처리 시 동작

선택한 요청은 한 건씩 순서대로 처리합니다. 일부가 만료되거나 다른 교사가 이미 처리했다면 그 학생의 오류를 표시하고 나머지는 계속 처리합니다. 성공한 출석을 취소하지 않습니다. 실패 요청을 자동으로 재시도하지 않으며, 다시 확인하고 선택해야 합니다.

검색·필터·페이지를 바꿔도 선택은 유지됩니다. 현재 화면 밖에 선택된 학생이 있으면 `outside this page/filter`와 인원수를 표시합니다. 선택 승인에는 이 학생들도 포함되므로 처리 전에 확인하거나 **Clear selection**으로 해제합니다. 새로 들어온 학생 요청은 자동 선택하지 않습니다.

처리 중에는 자동 조회 결과가 승인 결과를 덮어쓰지 않도록 합니다. 다른 수업으로 이동하면 아직 보내지 않은 요청은 중단합니다. 이미 서버에 보낸 요청은 완료될 수 있습니다. 조회가 실패하면 마지막으로 받은 데이터를 유지하면서 오류를 표시하므로, 다시 갱신해 확인해야 합니다.

이미 Present·Late·Absent로 저장된 학생에게 남은 대기 요청은 기존 출석을 덮어쓸 수 없습니다. 해당 요청에는 이미 출석이 저장되었다는 안내를 표시합니다. 수정하려면 수동 출석 기능을 사용합니다.

## DB와 실행 방법

기존 시작·종료 명령어를 그대로 사용합니다. 저장소 루트에서 실행합니다.

```powershell
# 전체 로컬 서버 시작
powershell -ExecutionPolicy Bypass -File .\data\local-dev\start.ps1

# 전체 로컬 서버 종료
powershell -ExecutionPolicy Bypass -File .\data\local-dev\stop.ps1
```

이미 실행 중이면 시작 명령이 재시작까지 하지는 않습니다. 코드를 바꾼 뒤 백엔드 재시작이 필요하면 종료 후 다시 시작합니다. 이 스크립트와 로그인 정보는 현재 PC의 Git 제외 파일이므로 다른 팀원의 PC에는 별도 로컬 설정이 필요합니다.

V6 마이그레이션이 `attendance_review_events` 이력 테이블과 인덱스를 추가합니다. 기존 V5 Flyway DB라면 새 백엔드를 시작할 때 자동 적용합니다. DB 초기화나 얼굴·계정 재등록은 필요하지 않습니다. **현재 PC에는 V6를 적용했고 백엔드도 재시작했습니다. 기존 데이터는 유지했습니다.** 프론트엔드와 Python 서버도 실행 중입니다.

이력에는 학생·처리자 참조, 처리 종류, 전후 상태와 시간을 저장합니다. 사진·얼굴 특징·유사도·결석 사유를 복사하지 않습니다. 학생 요청 반려는 `PENDING → REJECTED`로 기록되며 결석 처리가 아닙니다. 이 기능 적용 전의 이력은 복원하지 않습니다.

출석 변경과 이력 기록은 같은 트랜잭션으로 처리합니다. 실패한 작업의 이력은 남지 않으며 같은 사진·학생 요청 승인 재시도는 이력을 중복 생성하지 않습니다. 수동 저장은 같은 상태라도 다른 항목이 바뀔 수 있으므로 별도 이력입니다. 이름은 현재 계정 정보를 보여줍니다. 학생·수업 삭제 시 관련 이력도 삭제되고, 처리자 계정 삭제 시 처리자는 `Unavailable`로 표시됩니다. 별도 기간 만료 삭제 작업은 추가하지 않았으며 운영 전 출석 데이터 보관 정책을 정해야 합니다.

## 개발자 참고와 검증 결과

새 API는 `GET /api/sessions/{id}/attendance-review`이며 `attendance`, `requests`, `history` 배열을 반환합니다. 담당 교사·관리자만 접근할 수 있고 캐시하지 않습니다. CV 추론이 꺼져 있어도 조회와 수동 출석은 가능합니다. 사진 요청 승인은 기존 CV 활성화 조건을 유지합니다.

선택 승인은 기존 `POST /api/vision/check-ins/{id}/decision`을 재사용하며 서버가 매번 수업 권한·동의·명단 변경·만료·기존 출석을 검사합니다. 수동 수정도 기존 API를 재사용합니다. 주요 변경 파일은 `StudentCheckInQueue.tsx`, `useAttendanceReview.ts`, `attendanceReviewModel.ts`, `SessionDetail.tsx`, 백엔드 `AttendanceReviewController/History/Event`, 출석 저장 서비스와 V6 SQL입니다.

- 프론트엔드 빌드 및 테스트 343개 통과.
- 관련 백엔드 테스트 61개 통과.
- 별도 PostgreSQL에서 얼굴·학생 요청 관련 테스트 31개 통과.
- 빈 PostgreSQL DB 신규 설치와 V5→V6 전환, 기존 행 값 보존, ORM 검증 통과. 모듈 구조 검사 4개 통과.
- 1440px·390px 브라우저에서 20명 전체 표시, 21명 페이지 분할, 페이지 간 선택 유지와 새 요청 미선택, 선택 승인·부분 실패·반려·검색·필터·수동 수정 연결·이력·조회 실패 표시를 확인. 가로 넘침과 JavaScript 오류 없음.
- 현재 로컬 서버의 기존 수업 2개에서 관리자 인증 후 조회 API 응답과 실제 수업 상세 화면 로드를 확인. 이 확인 과정에서 사용자 출석을 변경하지 않음.
